## Notes
Derived by hand. serde derives serialize in declaration order: id, project, parent_id, container_id, app_id, mark, status. `AgentId`/`ProjectId` are newtype structs so serialize as bare strings. `AgentStatus` uses `rename_all = "snake_case"` and unit variants serialize as plain strings. `None` is `null`. mark = `mark_` + id with `-` replaced by `_`. `register_agent` sets container_id None and status Idle.

Agent A: `{"id":"golden-a","project":"golden-proj","parent_id":null,"container_id":null,"app_id":"agent.pi.golden-a","mark":"mark_golden_a","status":"idle"}`
Agent B: `{"id":"golden-b","project":"golden-proj","parent_id":null,"container_id":null,"app_id":"agent.pi.golden-b","mark":"mark_golden_b","status":"awaiting_human_input"}`
Golden = `[A,B]` or `[B,A]`, no spaces (`serde_json::to_string`); the trailing `\n` is stripped by `lines()`.

Constraints honored: only tests/subscribe_golden.rs created (plus this todo); no src/ change; no new deps; no fixed sleeps (readiness via polling); scratch in .development/ only; no commit; STATE_21.md untouched.

Risks:
- Ordering: `DaemonState.agents` is a `HashMap` and `broadcast_status` serializes `agents.values()` with no sort, so element order is randomized per process. A single fixed golden would flake about 50%. Plan accepts exactly the two permutations, each byte-exact. Making the order fixed needs a src/ change (out of scope).
- Cross-connection ordering: register on one connection and subscribe on another is not ordered, hence the probe loop in step 5.
