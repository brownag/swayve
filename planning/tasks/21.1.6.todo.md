# 21.1.6 -- G30 Socket-Level Slow-Consumer Recovery

Question 1.
- Anchors (main checkout): `broadcast_diff` is `src/daemon.rs` ~88. `TrySendError::Full` sets `*needs_snapshot = true`, and `sent` is only updated on a successful send. A snapshot is built only on the next `broadcast_diff` call. `handle_client` `SubscribeDiff` arm (~354) uses `mpsc::channel(32)` and a writer task that `write_all`s each message and blocks on a full socket buffer.
- Payload reasoning: a Unix stream socket buffer is about 208 KiB by default (`wmem_default`) plus the client's receive buffer. The writer therefore blocks after roughly 25-50 lines of ~8.2 KiB. The next 32 messages then fill the channel, and the remaining 200+ of the 300 hit `Full`. A 300 x 8 KiB stream is about 2.4 MB, an order of magnitude over the buffer, so a moderate kernel buffer change will not break it.
- `UpdateStatus` params carry no `app_id`. The large payload comes from `Register` and is re-serialized into every diff upsert.
- Convergence hazard: after a drop, `needs_snapshot` is set but a snapshot goes out only on the next broadcast. If the 300th update was dropped, no further broadcast follows and the draining client ends with stale state. Spec step 7 compares directly after reading, which would be flaky or fail. Hence items 7-8: drain until quiescent, then one trigger update, whose broadcast sends the recovery snapshot. Question 2.
- Cross-connection ordering: updates and the status query arrive on different connections, so a single query is not an ordering guarantee. Item 6 polls until the final status is visible, as the spec's "polling" allows.
- Constraints honored: no `src/` edits, only `tests/slow_consumer.rs` plus this file, no new dependencies, scratch in `.development/` only, no commit.
- How the test fails if the drop path is removed:
  - If `Full` stops setting `needs_snapshot` (just retains), no snapshot is ever sent after the first. The `>= 2 snapshots` assertion fails, and that is the primary guard.
  - If `try_send` is replaced by a blocking send, the daemon loop stalls behind the blocked writer. The daemon would never process all 300 updates, so the item 6 poll times out and the test fails.
  - Note that dropping only `needs_snapshot` would still self-heal state (the diff is computed against `sent`), so the snapshot count assertion is what proves the recovery path was taken.
- Risks: timing (300 ms quiescence is a heuristic; the only effect of a premature stop is that the trigger update is dropped as `Full` again and the final read then times out). I could loop the trigger if needed. Also, the test sends via the 32-slot event channel, which backpressures the writer connection but does not drop.
