# Task 4.1 — Implement Hierarchical Focus Algorithm

## Goal
Replace the naive Focus handler in `src/daemon.rs` (lines 243–265) with hierarchical sibling-cycling logic that enables parent-to-child and child-to-sibling focus navigation based on agent window relationships.

## Tasks
- [x] **1. Understand focus state derivation approach**
  - Clarify how to determine "currently focused" agent window without querying Sway (performance concern)
  - Verify if static/thread-local tracking or heuristic is preferred over Sway connection per event
  
- [x] **2. Extract currently-focused agent helper function**
  - Create `get_focused_agent(state: &DaemonState) -> Option<AgentId>` helper
  - Decide: query Sway tree, use last-focused heuristic, or derive from mark tracking
  
- [x] **3. Implement sibling-cycling logic**
  - Write core algorithm:
    - If no agents: return (no-op)
    - If no currently-focused: focus first agent (sorted by con_id)
    - If focused is parent with children: cycle to first child
    - If focused is child: cycle to next sibling (by con_id) or back to parent
    - If focused is orphan: no-op
  
- [x] **4. Replace Focus match arm (lines 243–265)**
  - Remove naive "focus first" logic
  - Insert new hierarchical cycling logic
  - Send `SwayCommand::FocusWindow { mark }` with target
  
- [x] **5. Write unit test: `test_hierarchical_focus` in `src/daemon.rs` tests module**
  - Mock DaemonState with parent + 2 children
  - Test case 1: No agents → no-op
  - Test case 2: Single agent → focus it
  - Test case 3: Focused on parent → cycle to first child
  - Test case 4: Focused on first child → cycle to second child
  - Test case 5: Focused on last child → cycle back to parent
  - Verify correct `FocusWindow` commands sent via mpsc channel
  
- [x] **6. Verify with `cargo check` and `cargo test --lib daemon::tests::test_hierarchical_focus`**

## Notes
**Facts Discovered:**
- `DaemonState` contains: `agents: HashMap<AgentId, AgentWindow>`, `con_to_agent`, `pid_to_agent`
- `AgentWindow` has fields: `id`, `parent_id: Option<AgentId>`, `container_id: Option<i64>`, `mark: String`
- Current Focus handler (lines 243–265): collects agents, sorts by con_id, focuses first one unconditionally
- CLI uses `swayipc_async::Connection::get_tree()` to find focused node (see cli.rs:316-344)
- `DaemonEvent::Focus` is defined but not yet triggered anywhere in codebase (no event_tx.send(Focus) found)
- No focus-tracking state currently exists in DaemonState; constraint forbids adding new fields

**Constraints Honored:**
- No new fields added to DaemonState
- Do not change WindowCreated/WindowDestroyed handlers
- Do not call LayoutManager
- Focus state derived from existing relationships (parent_id, container_id)

**Risks:**
- Determining "currently focused" is ambiguous without state tracking; need clarification on approach
- Sway connection creation per Focus event may be inefficient if Focus events fire frequently
- No visibility into how/when Focus events are triggered (not wired in current code)

## Questions
1. **Focus state derivation approach**: Should we query Sway's tree on every Focus event (as CLI does), use a thread-local last-focused tracker, or apply a simpler heuristic? Query is reliable but may be expensive if Focus fires rapidly.

2. **Sway connection in daemon loop**: The `run_daemon_loops()` function does not maintain a Connection. Should we create one per Focus event (async), or prefer a stateless heuristic?

3. **"Currently focused" fallback**: If focus query/tracking fails, should we default to "no currently-focused agent" (restart cycling at first agent) or re-focus the previous target?

4. **Focus event trigger source**: Is the Focus event expected to be triggered by CLI, external IPC, or another mechanism? (Affects test assumptions)

5. **Sibling sort order**: Spec says "sort children by con_id"; should we pre-sort all agents by con_id once at handler entry to ensure consistent cycling, or sort dynamically within each branch?
