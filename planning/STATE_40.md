### 40.1.1 — Establish Session and Window Identity Contract

- **Status:** Complete; this task found no automatic identity source, so downstream work initially paused pending the discovered 40.1.2 investigation and user decision. The user later approved explicit binding as D10; no heuristic mapping is authorized.
- **OpenCode v2.3.2 sources:** pinned tag [`v2.3.2`](https://github.com/anomalyco/opencode/tree/v2.3.2), commit `c0ad18b402eb2827fc1ee71c171b1177b3fc02d1`. First-party files: `packages/plugin/src/promise/{plugin,event,session,adapter}.ts`; `packages/protocol/src/groups/session.ts`; `packages/core/src/{session.ts,bus.ts,session/{store,sql,info,projector,event}.ts}`.
- `ctx.session.list` is read-only and does not prompt, call tools, or read message history (`plugin/src/promise/adapter.ts`, session list endpoint/handler). It returns `{data,cursor}`; default limit is 50, with opaque `cursor.next` pagination (`protocol/src/groups/session.ts`; `core/src/session.ts`). Continue until no next cursor, carrying the same filters.
- The list supports `project`, `directory`, `subpath`, `parentID`, `archived`, and `limit`; the store applies provided filters and defaults to no parent filter, so child sessions are included (`schema/src/session.ts`; `core/src/session/store.ts`). Use a verified project/directory filter; do not confuse project scope with window scope. `Session.Info` contains ID, optional `parentID`, project ID and location directory, but no window/PID/app identity (`schema/src/session.ts`; `core/src/session/info.ts`).
- `ctx.event.subscribe` adapts a volatile live stream; bus source documents “from now on, nothing before or across a disconnect” (`packages/plugin/src/promise/adapter.ts`; `packages/core/src/bus.ts`, `Subscribe`). It does not replay/backfill. Subscribe before enumeration and deduplicate IDs to cover create/list races; events missed before subscription require enumeration, and missed deletes cannot be inferred from list absence safely.
- `session.created` is published during actual session creation and includes `sessionID`, project, location and optional `parentID`; setup does not synthesize it for existing sessions (`core/src/session.ts`; generated event type `packages/client/src/promise/generated/types.ts`). Lifecycle events carry `data.sessionID`; `session.deleted` is a durable event with `data.sessionID` (`packages/schema/src/session-event.ts`; generated types). Removal publishes deletion, removes the session, and recursively removes children through the same removal path (`core/src/session.ts`; deletion projector `core/src/session/projector.ts`), so the event is authoritative for the specific deleted ID.
- **Identity blocker:** neither `Session.Info`/`session.created` nor plugin `Context` provides a Sway `con_id`, window `app_id`, or a per-window PID. `ctx.location` is a project/location context, not a window handle. The plugin’s `process.pid` identifies the plugin process, not a particular session’s hosting window (`.opencode/plugins/swayve.ts:21–30,48–58`). Shared directory and session `parentID` do not identify a window.
- **Swayve trace:** Sway window events provide `con_id`, `app_id`, optional PID (`crates/swayve/src/sway.rs:107–120,144–166`). Daemon binds only an exact matching `app_id` (`daemon.rs:209–274,707–719`); registration reuses current container/status and indexes the supplied PID (`daemon.rs:151–190`). Optional `/proc` ancestry auditing finds a registered process ancestor to infer `parent_id`, not a session/window identity (`daemon.rs:721–743,821–854`). Window destruction removes the bound agent; there is no session-agent retirement IPC (`daemon.rs:277–302`; `crates/swayve-types/src/lib.rs:112–184`).
- **Relationship semantics:** `parent_id` drives layout grouping and focus traversal (`crates/swayve/src/layout.rs:64–96`; `daemon.rs:779–818`; ADR 0007). HUD is a flat list with no separate hosting-window relationship (`crates/swayve-hud/src/client.rs:78–117`). Do not overload `parent_agent_id`; retain ADRs 0003/0004/0006/0007/0009/0012.
- **Recommendation / gate:** enumeration and authoritative deletion events are available, but exact window association is not established by source/API evidence. Keep sessions explicitly unassociated; do not implement 40.2.1, 40.3.1, 40.3.2, or 40.4.1 absent a separately approved design that supplies/verifies exact identity. No guessed project-, title-, session-ID-, or PID-based association.
- **Focused test:** `node --experimental-strip-types --test integrations/opencode/sidecar.test.mjs` — 4/4 passed; existing `MODULE_TYPELESS_PACKAGE_JSON` warning only. No live OpenCode/Sway interaction, implementation edit, commit, staging, or remote action.

### Discovered Task 40.1.2 — Investigate Verifiable Session-to-Window Identity Options

- **Status:** Complete; added to Wave 1 after 40.1.1 established that OpenCode itself exposes no Sway window identity.
- **Scope:** Read-only investigation of explicit per-window/session binding and OpenCode server/process-to-Sway-window mapping (plus evidence-backed alternatives); may update this state report only.
- **Gate:** Explicit user-attested binding was recommended and approved by the user; recorded as D10. Automatic association remains prohibited.
- **Evidence reviewed:** OpenCode v2.3.2 pinned source/API findings recorded in 40.1.1; `.opencode/plugins/swayve.ts`; `integrations/opencode/README.md`; Sway IPC `GET_TREE`/window-event documentation ([sway-ipc(7)](https://man.archlinux.org/man/sway-ipc.7.en)); `crates/swayve/src/{sway.rs,daemon.rs,config.rs}`; `crates/swayve-types/src/lib.rs`; `README.md`; accepted ADRs 0003, 0004, 0006, 0007, and 0009.
- **Option A — explicit user-provided binding or launch metadata:** OpenCode session records and `session.created` expose session/project/location/parent metadata, not a Sway `con_id` or window identity (40.1.1, OpenCode `Session.Info` and event findings). Current plugin uses `process.pid` and session ID as registration metadata; neither is a window signal (`.opencode/plugins/swayve.ts:21–58`; `integrations/opencode/README.md:18–23`). Sway IPC exposes window `id`/`app_id`/PID, while this Swayve listener receives `con_id`, app ID, and optional PID (`sway-ipc(7)`, GET_TREE/window event; `crates/swayve/src/sway.rs:107–166`). Existing Swayve launch config supports app-ID and command templates, and spawned clients receive identity environment (`config.rs:117–126`; ADR 0006), but OpenCode's project-local plugin is not launched by Swayve per session, so this metadata path does not currently carry a session/window pair. A static config mapping would be stale/ambiguous across dynamic sessions and window recreation unless the user explicitly maintains it.
- **Option A assessment/recommendation:** A narrow explicit bind is viable only as a user-attested operation that names both the exact OpenCode session and the chosen Swayve window-agent identity, followed by daemon validation that both records exist and the target is unambiguous. The user action—not directory/title/session-ID/PID inference—supplies the association. On absent, conflicting, or stale endpoints, leave the session unassociated and require a new explicit bind; window destruction must clear the link, and session deletion may retire only on the authoritative event established in 40.1.1. This is a proposed contract, not an existing capability or approval. It adds a bind/unbind interaction and daemon relation, with lifecycle handling; do not repurpose `parent_agent_id` (ADR 0007). **Falsifiable validation:** with two sessions and two registered windows, explicitly bind each selected pair, verify exact distinct associations, then attempt unknown/stale endpoints and verify no association is created; repeat after closing/recreating a window and verify the old binding is not silently reassigned. A deliberate user-selected cross-pair should bind only if that exact pair was selected, demonstrating that no heuristic is choosing.
- **Option B — OpenCode server/process identity mapped to Sway windows:** Sway publishes the PID of the process owning a window and may expose it in `GET_TREE`; OpenCode plugin `process.pid` identifies the plugin process, not its session's window (40.1.1; `.opencode/plugins/swayve.ts:21–30,48–58`). A process-tree relationship could be evidence only if a per-window process is a unique, live descendant of a known server and each session is independently tied to that process. The reviewed OpenCode API/source provides no per-session process/window handle. Shared server instances can serve multiple projects/sessions/windows; tabs may share one window or move among windows; a server PID can therefore match multiple candidate windows or none. PID reuse after exit and intermediary/reparented processes make ancestry time-dependent. Swayve's process-tree audit walks to a registered ancestor specifically to infer `parent_id`, not a session/window pair (`daemon.rs:721–743,821–854`; ADR 0007); its PID index does not add session provenance. **Failure behavior:** any multiple/zero candidate, stale PID, or missing ancestry must yield no association, never a guess. **Footprint/validation:** a reliable automatic design would need new first-party per-session process provenance plus lifetime-safe process identity and a one-to-one window/session signal; PID ancestry alone is insufficient. A falsifiable test would need two sessions in one shared server and multiple windows, plus server restart/PID reuse and tab movement, proving unique correct mapping every time; the current source/API lacks the signal needed to pass this test.
- **Other evidence-backed alternatives:** Sway window `app_id` and Swayve's unique-app-ID convention identify a Swayve-launched agent window exactly (ADR 0006), but the OpenCode plugin does not launch each session's window and no OpenCode session-to-app-ID contract exists. Focus, title, project directory, session ID string, plugin PID, and server PID alone are not identity evidence; titles can change, project directories are shared, and session IDs are not Sway window properties. None is a safe substitute for explicit pairing.
- **Recommendation / decision point:** Prefer explicit user-attested session-to-window-agent binding if the product accepts a deliberate bind action and its implementation/UX footprint. If automatic, zero-action association is required, conclude no currently viable contract is demonstrated and keep sessions unassociated. The user approved the explicit bind contract, including fresh binding after stale/recreated windows; recorded as D10. This does not approve an ADR change. ADR 0003/0004/0006/0007/0009 remain constraints.
- **Validation performed:** Read-only source and documentation inspection only. No tests, live OpenCode/Sway interaction, implementation changes, staging, commits, or remote actions.
- **Decision:** User approved explicit user-attested session-to-window binding, with fresh binding required for stale/recreated windows. Recorded as D10 in `EXECUTION_PLAN_40.md`; no heuristic association is authorized.
